ARTICLES / TELEPHONY SECURITY

MMI and USSD security: closing an Android permission gap.

A telephone-call permission should not automatically grant an application the ability to change carrier services. Jaguar ROM adds authorization checks across Android 11's telephony and Telecom paths.

The security boundary: USSD and MMI strings are not ordinary telephone numbers. Some query carrier services; others can alter network-side settings such as call forwarding. Jaguar aims to keep those operations under trusted or user-approved control.

Why MMI and USSD matter

Android accepts special dial strings made from digits, asterisks and hash characters. MMI (Man–Machine Interface) commands and USSD (Unstructured Supplementary Service Data) requests can query account information or invoke carrier services. Some supplementary-service commands can register call forwarding, potentially diverting incoming calls to another number. Such forwarding can persist on the carrier network even after the initiating app is removed.

The concrete risk: an attacker receives the victim’s incoming calls

The research describes how the unconditional call-forwarding MMI sequence **21*<number># can register a destination number with the carrier. If an attacker can cause a vulnerable dialing path to execute that sequence with a number they control, and the carrier accepts the request, incoming calls to the victim can be forwarded to the attacker’s number instead of ringing the victim’s phone. This is not merely a theoretical change to a phone setting: it can redirect real calls, including calls containing sensitive information.

Because call forwarding is a network-side service, the redirection may continue until it is disabled, even if the application that initiated it is removed. The precise behavior depends on the carrier, subscription and forwarding configuration. The published research demonstrated call forwarding on a live network; it does not establish that every carrier or Android configuration is exploitable.

The CALL_PHONE permission is presented to users as permission to make and manage phone calls. It does not clearly convey that certain dial strings can modify network services. The distinction between making a call and executing a carrier-control command is therefore important.

The research and Google's response

On October 9, 2026, security researcher Karan Saini published 1-click MMI execution in Android. He documented a chain involving an installed third-party dialer with CALL_PHONE, a browser-reachable dialing entry point, and a user tapping a link. Under the demonstrated conditions, the dialer executed an MMI command without an advance confirmation prompt. The research included a live-network demonstration of call forwarding.

Saini reported the issue to Google's Android security team on September 12, 2026. Google closed the report on September 17 as “Won't Fix (Infeasible)”, characterizing the demonstrated exploit as insecure third-party dialer deeplink handling rather than a vulnerability in Android itself. In its published response, Google said it was considering future platform improvements to help prevent third-party applications from making this kind of mistake, but did not classify those improvements as a direct vulnerability fix.

That position effectively places much of the responsibility on third-party dialers to validate externally supplied dialing strings. But application-level validation does not establish that the AOSP Dialer or Android's shared telephony infrastructure is protected along every invocation path. A trusted system dialer is not automatically immune to misuse merely because it is not a third-party application. This is a question about where the platform should enforce authorization—not proof that the identical browser-to-dialer exploit works against AOSP Dialer.

Saini also documented a separate Android 17 emulator finding in which a Telecom handoff lost the original caller identity, potentially causing an MMI request to be evaluated under a privileged application's identity. He reported that issue separately; Google classified it as a duplicate of an internal issue. That finding was emulator-tested, not validated as a live carrier-network exploit, and should not be conflated with Jaguar's Android 11 tests.

Jaguar's defense-in-depth approach

Jaguar ROM implements checks in Android's telephony and Telecom infrastructure, rather than relying exclusively on individual dialers to reject sensitive strings. The implementation distinguishes trusted system callers from untrusted third-party applications and uses user approval for supported direct USSD requests.

1. Direct USSD requests

At the PhoneInterfaceManager.handleUssdRequest() entry point, Jaguar checks the requesting identity. Trusted system, phone and designated SIM/eUICC components retain necessary access. Untrusted direct USSD requests are subject to the ROM's authorization and confirmation handling; requests not approved are rejected.

2. Telephony MMI processing

Additional checks were developed around GSM/CDMA dialing and MMI interpretation, including GsmCdmaPhone and GsmMmiCode. These paths matter because special strings can be interpreted as MMI operations instead of ordinary numbers. The investigation also considered IMS-related handling and fallback paths. The available test record does not establish a separate, exhaustive end-to-end IMS USSD block across all carrier configurations.

3. Telecom call initiation

Jaguar also protects potentially sensitive MMI requests arriving through Telecom, including ACTION_CALL and TelecomManager.placeCall(). In device testing, a dedicated untrusted test application attempting the latter route was rejected with this log message:

Blocked Telecom MMI request: uid=10345, package=com.android.ussdtest

The ACTION_CALL MMI route was tested as well. These checks address attempts to bypass direct-USSD authorization by using an ordinary call-placement interface.

Testing: blocking sensitive operations without breaking calls

Development testing on the OnePlus 9 Pro included untrusted direct-USSD attempts, ACTION_CALL, TelecomManager.placeCall(), and verification of normal call behavior. The untrusted Telecom MMI attempt was explicitly logged as blocked. Regular telephone calls continued to work, and legitimate USSD operations through the trusted AOSP Dialer remained functional.

The tests demonstrate the exercised paths, not every conceivable carrier-specific command or IMS configuration. Jaguar's trusted-caller exemptions are intentional, so an already-compromised privileged component represents a different threat model.

Why the platform boundary matters

Checking only a third-party application's deeplink leaves protection dependent on every call-capable application's implementation. Jaguar instead places checks at multiple system entry points. The intended rule is simple: permission to place a telephone call must not silently become unrestricted permission to execute sensitive carrier commands.

This article describes development testing and the published security research, not an independent security audit or a guarantee against every telephony-related attack. The researcher's Android 17 findings and Jaguar's Android 11 implementation are separate investigations.
